## 1. 등장인물 — 누가 누구인가

### Cloudflare Workers

Cloudflare 가 파는 서버리스 실행 환경. 코드를 올리면 전세계 엣지에서 돈다.
AWS Lambda 같은 것이라고 보면 된다.

### workerd

**Workers 를 실제로 실행하는 엔진.** C++ 로 짜인 런타임이다.
Cloudflare 가 오픈소스로 공개했고, 프로덕션에서도 이게 돈다.

→ **우리 이야기의 "고아 프로세스"가 바로 이 workerd 다.**

### Miniflare

**내 노트북에서 Workers 를 흉내내는 시뮬레이터.** 내부적으로 workerd 를 프로세스로 띄운다.

공식 README 왈:
> Miniflare is a **lower level API designed for tools creators**

즉 **사람이 직접 쓰는 게 아니라, 다른 도구가 가져다 쓰는 라이브러리**다. 이게 중요하다 (§4).

### Wrangler

**Cloudflare 공식 CLI.** `wrangler dev`, `wrangler deploy` 같은 걸 치는 그 도구.
내부에서 Miniflare 를 쓴다.

### 관계도

```
사람이 치는 것:  wrangler dev
                    ↓ (내부에서 사용)
                 Miniflare        ← "도구 제작자용 라이브러리"
                    ↓ (프로세스로 띄움)
                 workerd          ← 실제 코드가 도는 엔진
```

**wrangler 말고도 Miniflare 를 쓰는 도구가 여럿 있다** — 이게 §4 의 핵심이다.

## 2. 무슨 문제인가

`wrangler dev` 를 쓰면 workerd 가 뜬다. 개발 끝나고 종료하면 workerd 도 같이 죽어야 한다.

**그런데 안 죽고 남는 경우가 있다.** 부모가 죽었는데 자식만 살아남은 상태 = **고아 프로세스**.

내 맥에서 실제로 세어보니 **17개**가 떠 있었다. 가장 오래된 건 **4일 넘게** 살아있었다.

### "고아"를 어떻게 알아보나

유닉스에서 모든 프로세스는 부모가 있다. 부모가 죽으면 자식은 **PID 1(init/launchd)** 이 입양한다.
그래서 `ps` 에서 **부모 = 1** 이면 "원래 부모가 죽었는데 혼자 남았다"는 뜻이다.

```
PID     부모   메모리    경과
54647   1     1.4MB    4일 10시간   ← 고아
```

### 피해는 큰가

솔직히 **작다.** 17개 합쳐서 메모리 30MB 남짓, CPU 는 0%.
다만 **재시작할 때마다 하나씩 쌓인다**는 게 문제고, 이슈 스레드엔 CPU 95% / RAM 5GB 를
겪었다는 보고도 있다 (내 케이스와는 양상이 다르다 — 과장하면 안 됨).

## 3. 원인 — 신호(signal) 이야기

### 신호가 뭔가

OS 가 프로세스에게 보내는 짧은 알림. 종류마다 뜻이 정해져 있다.

| 신호 | 번호 | 언제 | 뜻 |
|---|---|---|---|
| **SIGHUP** | 1 | 터미널 끊김 | "네가 붙어있던 터미널이 사라졌다" |
| **SIGINT** | 2 | Ctrl+C | "중단해" |
| **SIGKILL** | 9 | `kill -9` | "즉시 죽어" (거부 불가) |
| **SIGTERM** | 15 | `kill` 기본 | "정리하고 끝내" |

**SIGHUP = SIG + HUP(hang up, 전화 끊기).** 1970년대 전화선으로 접속하던 시절 유래.
지금은 "터미널 창 닫기" 정도로 쓰인다.

### 핵심: 신호는 가로챌 수 있다

- **핸들러가 없으면** → 기본 동작 (SIGHUP 은 즉사)
- **핸들러를 등록하면** → "죽기 전에 이것부터 해라" 를 끼워넣을 수 있다

### Miniflare 의 문제

`packages/miniflare/src/exit-hook.ts` 는 이렇게 돼 있었다:

```js
process.on("exit", onExit);
process.on("SIGINT", onSignalInt);    // Ctrl+C     → 처리함
process.on("SIGTERM", onSignalTerm);  // kill       → 처리함
// SIGHUP 은 없음                        ← 여기가 구멍
```

그래서 SIGHUP 이 오면:

```
SIGHUP 도착
  → 핸들러 없음 → Node 가 그냥 즉사
  → 정리 콜백(dispose) 실행 안 됨
  → workerd 를 죽이는 kill("SIGKILL") 코드에 도달조차 못 함
  → workerd 살아남음 → 고아
```

**중요**: workerd 를 죽이는 코드는 **원래부터 잘 있었다.** 거기 도달을 못 한 것뿐이다.

이게 14개월 전 메인테이너가 남긴 말과 정확히 맞는다:
> "SIGKILL 이 실제로 수행됐다면 workerd 가 고아로 남을 방법이 없다.
>  miniflare 가 **어떤 상황에서** SIGKILL 전송에 실패하는 게 분명하다"

그 "어떤 상황"이 SIGHUP 이었다.

## 4. 반전 — 터미널 닫기로는 재현이 안 된다

처음엔 "터미널 창 닫으면 SIGHUP 오니까 고아 생긴다"고 생각했다.
**직접 해보니 안 생겼다.** iTerm2, Zed 터미널, tmux 셋 다.

### 왜 안 생기나 — 프로세스 그룹

유닉스는 프로세스를 **그룹**으로 묶는다. 터미널이 창을 닫을 때는 **그룹 전체**에 SIGHUP 을 보낸다.

```
【터미널에서 wrangler dev 실행】
  터미널 ─┬─ node(wrangler)   PGID 같음
          ├─ workerd          PGID 같음  ← workerd 도 SIGHUP 직접 받음
          └─ workerd          PGID 같음

  창 닫기 → 전부 SIGHUP 받음 → workerd 가 스스로 죽음
  → Miniflare 의 정리 로직이 동작할 필요조차 없다
```

즉 **wrangler dev 는 우연히 보호받고 있었다.**

### 그럼 언제 터지나 — Miniflare 를 "임베드" 할 때

§1 에서 말한 것: Miniflare 는 **도구 제작자용 라이브러리**다.
실제로 여러 도구가 `new Miniflare(...)` 로 직접 가져다 쓴다:

| 도구 | 위치 |
|---|---|
| `vitest-pool-workers` (Workers 테스트 러너) | `src/pool/index.ts:731` |
| `@cloudflare/vite-plugin` | `src/context.ts:51` |
| `remote-bindings` | `ProxyController.ts:115` |

이 경우 부모는 wrangler 가 아니라 **vitest/vite 프로세스**다.
CLI 가 만들어주던 프로세스 그룹 보호가 **없다.**

```
【Miniflare 를 임베드】
  vitest 프로세스  ← SIGHUP 은 여기만 받음
     └─ workerd    ← 신호 못 받음
  → exit-hook 만이 유일한 방어선인데, 그게 SIGHUP 을 안 들었다
  → 고아 발생
```

**결정적**: `vitest-pool-workers` 는 `dispose()` 를 **아예 호출하지 않는다** (898줄 전체에 없음).
즉 **종료 시 이 exit-hook 에 100% 의존**한다.

### 실측 (6회, 깨끗하게 갈림)

| Miniflare 임베드 + SIGHUP | 결과 |
|---|---|
| 수정 전 | **고아 3/3** |
| 수정 후 | **정리 3/3** |

그리고 이건 이슈에 실제로 보고된 케이스와 맞는다:
- koistya: "**VSCode + Vitest 확장**에서 좀비 workerd"

## 5. 수정 내용 — 12줄

`packages/miniflare/src/exit-hook.ts`:

```js
function onSignalHup() {
  runCallbacks();          // 정리 작업 실행
  process.exit(128 + 1);   // SIGHUP 기본 동작 재현
}

process.on("SIGHUP", onSignalHup);              // 등록
process.removeListener("SIGHUP", onSignalHup);  // 해제
```

기존 `onSignalTerm` 과 **완전히 같은 모양**이고 종료 코드만 다르다.

### 왜 원래 없었나 (중요)

"실수로 빠뜨린 것"이 아니다. **상속된 것**이다.

- 이 파일은 `exit-hook` 이라는 npm 패키지를 대체한 것 (PR #13515)
- **그 패키지도 SIGHUP 을 안 듣는다** (직접 확인함)
- 일반 CLI 라면 무해하다 — 그냥 죽으면 그만이니까
- **하지만 Miniflare 는 자식 프로세스를 소유한다.** 그게 다른 점이다

참고로 `signal-exit` 같은 다른 라이브러리는 SIGHUP 을 **듣는다.** 즉 라이브러리마다 선택이 갈리는 문제이지,
"누가 실수했다"가 아니다.

## 7. 아직 모르는 것 / 못 고치는 것

### Windows 미검증

Node 문서상 Windows 도 콘솔 창 닫을 때 SIGHUP 이 발생한다.
`exit-hook.ts` 에 플랫폼 분기가 없으니 같은 구멍이 있을 것으로 보인다.

**다만 CI 로 측정이 안 된다.** Windows 에서 `process.kill()` 은 SIGHUP 을 전달 못 한다
(Node 문서: SIGINT/SIGTERM/SIGKILL 만 가능). 실기기에서 진짜 콘솔 창을 닫아야 한다.
→ 출근해서 `run-experiment.ps1` 로 확인 예정.

### 이 수정으로 안 고쳐지는 것

- **`kill -9` 나 크래시**: SIGKILL 은 핸들러 등록 자체가 불가능하다. 원리상 못 막는다.
- **내 맥의 고아 17개**: 이것들은 다른 경로다. 각자 다른 프로세스 그룹에 있고
  그룹 리더는 이미 죽었다. 신호가 아예 안 간 것으로 보이는데, **정확한 원인은 특정 못 했다.**

### 근본 해결책은 따로 있다

이슈 스레드에서 이미 나온 얘기:
- **프로세스 그룹 단위로 죽이기** (danawoodman 제안)
- **`tree-kill` 패키지** (petebacondarwin 검토)

이쪽이 크래시 케이스까지 커버한다. 내 12줄은 그것과 **충돌하지 않고**,
원인 하나를 확실히 없애는 작은 수정이다.

> 참고: `~/devglow` 가 실제로 이 방식을 쓴다. macOS 는 프로세스 그룹 + pgrep 트리 스냅샷,
> Windows 는 커널 Job Object 로 "부모 죽으면 자식도 죽음"을 보증한다.

## 9. 이 조사에서 배운 것 (일반화)

1. **"실험했는데 결과가 안 나왔다" ≠ "가설이 틀렸다."**
   프로세스 그룹 전체에 신호를 보내면 측정 대상이 신호를 직접 받아버려서 측정 자체가 무의미해진다.
   측정하려는 것을 격리해야 한다.

2. **exit code 0 을 믿지 말 것.** `pnpm install` 과 `pnpm check` 둘 다 실패했는데 0 을 냈다.
   로그 본문을 봐야 안다.

3. **CI 잡이 초록색이어도 믿지 말 것.** 1회차에서 Windows 6잡이 전부 success 였는데
   실제론 18회 전부 STARTUP_FAIL(측정 실패)이었다. **원자료를 열어볼 것.**

4. **`Number("") === 0` 이고 `kill(0, SIG)` 은 자기 프로세스 그룹 전체를 죽인다.**
   이걸로 CI 가 두 번 자살했다. `Number.isFinite` 로는 부족하고 **0 을 명시적으로 거부**해야 한다.

5. **추측을 사실처럼 쓰지 말 것.** "메인테이너가 tree-kill 도입을 예고했다"고 썼다가,
   확인해보니 **14개월 전 "might" 한 마디**였고 그 뒤 관련 코드를 여러 번 고치면서도 안 넣었다.
