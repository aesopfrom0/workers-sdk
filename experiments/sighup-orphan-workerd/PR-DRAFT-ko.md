## 본문

**#9193 관련.** 고아 `workerd` 로 가는 **재현 가능한 경로 하나**를 막는다. 이슈 전체를 고치는 건 아니고, 남은 경로는 마지막에 적어둔다.

`packages/miniflare/src/exit-hook.ts` 는 `exit`, `SIGINT`, `SIGTERM`, IPC `message` 를 듣지만 **`SIGHUP` 은 안 듣는다.** 터미널 창을 닫으면 SIGHUP 이 오는데, 핸들러가 없으니 Node 가 기본 동작으로 그냥 종료한다. `src/index.ts` 에 등록된 dispose 콜백이 실행되지 않고, `src/runtime/index.ts` 의 `runtimeProcess.kill("SIGKILL")` 까지 **도달조차 못 한다.** 그래서 `workerd` 가 부모 없이 남는다. 재시작할 때마다 하나씩 쌓인다.

스레드에서 이미 형태는 짚혔다. @kentonv 는 "miniflare 가 **어떤 상황에서** SIGKILL 전송에 실패하는 게 분명하다"고 결론지었고, @petebacondarwin 은 부모 프로세스가 "**정리 없이 죽는**" 게 문제라고 했다. **SIGHUP 이 바로 그 '어떤 상황'이고, 그 '정리 없이 죽는' 방식 중 하나다.** SIGKILL 코드는 멀쩡히 잘 있다. 다만 그 줄에 도달을 못 할 뿐이다. 추가한 리스너는 기존 `onSignalTerm` 과 똑같은 모양이고 종료 코드만 다르다.

### 측정

**신호는 부모에게만 보낸다.** `workerd` 가 직접 받으면 스스로 죽어버려서 아무것도 측정이 안 되기 때문이다. 조합당 3회, wrangler 4.107.0 + miniflare 4.20260701.0, GitHub 러너 기준:

| OS | | SIGHUP | SIGTERM | SIGINT |
|---|---|---|---|---|
| Linux | 수정 전 | **고아 3/3** | 정상 | 정상 |
| Linux | 수정 후 | **정상 3/3** | 정상 | 정상 |
| macOS | 수정 전 | **고아 3/3** | 정상 | 정상 |
| macOS | 수정 후 | **정상 3/3** | 정상 | 정상 |

앞서 macOS 에서 30회 돌린 것도 같은 결과였다 (수정 전 5/5 고아, 후 0/5). SIGTERM 과 SIGINT 는 양쪽 다 정상이라 **원래 잘 되던 경로는 안 건드렸다.** SIGHUP 일 때는 임시 디렉토리도 같이 새고 있었는데(`removeDirSync` 가 같은 dispose 콜백 안에 있음) 그것도 같이 없어진다.

**손으로 재현하려면**: `wrangler dev` 띄우고, `wrangler-dist/cli.js` 프로세스에 SIGHUP 을 보낸다 (프로세스 **그룹**에 보내면 안 됨 — workerd 가 직접 받으면 안 되니까). 그 다음 부모가 init 으로 바뀐 workerd 가 있는지 본다.

### 이 수정이 못 고치는 것

SIGHUP 은 고아 workerd 로 가는 경로 **하나**이지 전부가 아니다. 부모에 `SIGKILL` 을 보내는 경우나 wrangler 자체가 크래시하는 경우는 **이 방식으로는 원리상 못 막는다.** 위 데이터를 모으는 중에 **부모가 살아있는데도 고아가 생기는 걸** 봤으니 다른 경로가 최소 하나 더 있다. #9193 의 "유휴 서버", "크래시 루프" 보고들은 아마 그 다른 경로일 것이고, 그래서 `Fixes` 가 아니라 `Related to` 로 걸었다.

**Windows 는 미검증이다.** `exit-hook.ts` 에 플랫폼 분기가 없고 Node 가 Windows 에서도 콘솔 창 닫힐 때 SIGHUP 을 발생시키니 같은 구멍이 있을 것으로 보인다. 다만 Windows 에서는 `process.kill()` 로 SIGHUP 을 전달할 수 없어서 CI 로 측정이 안 된다. **근거 없는 숫자를 내놓느니 안 밝히는 쪽을 택했다.**

프로세스 **그룹** 방식이나 `tree-kill` (스레드에서 @danawoodman, @petebacondarwin 이 언급) 은 크래시 케이스까지 커버한다. 이 PR 은 그것과 충돌하지 않는다. **12줄로 원인 하나를 확실히 없애고**, 프로세스 spawn 방식은 안 건드린다. 더 큰 변경은 그 위에 얹으면 된다.

## ⚠️ 2026-08-17 정정 — "터미널 닫기" 서사는 반증됐다

**수동 실험 2회로 반증.** iTerm2 창 닫기, Zed 터미널 탭 닫기 — **둘 다 고아 0개.**

이유: 터미널에서 직접 `wrangler dev` 를 띄우면 **workerd 가 터미널과 같은 프로세스 그룹**에 들어간다.
창을 닫으면 커널이 그룹 전체에 SIGHUP 을 보내므로 **workerd 가 신호를 직접 받고 스스로 죽는다.**
miniflare 의 정리 로직이 동작할 필요조차 없다.

→ **고아가 생기려면 workerd 가 신호받는 그룹 "밖"에 있어야 한다.**
   즉 사람이 셸에 타이핑하는 게 아니라, 다른 도구가 dev 서버를 띄우는 경우다.

### hexaco 고아 16개의 진짜 원인은 특정 못 했다

| | |
|---|---|
| 현재 Zed 시작 | 8/16 12:19 |
| 고아 15개 생성 | **8/12 ~ 8/15** (이전 Zed 인스턴스들) |
| 고아 1개 | 8/16 13:06 |

각 고아가 **서로 다른 PGID** 이고 그 그룹 리더는 전부 죽어 있다.
Zed 소스(`crates/terminal/src/pty_info.rs:148-163`)를 보면
`killpg(tcgetpgrp(pty), SIGKILL)` + 셸 PID 단일 kill 뿐이라 **프로세스 트리를 순회하지 않는다.**
정황은 맞지만 **재현은 못 했다.**

**Zed 이슈로 내지 않기로 한 이유**:
- archive 는 스레드 목록 정리일 뿐 프로세스를 안 죽인다 (스레드는 계속 살아있는 구조)
- 재현 조건이 "Zed 를 껐다 켠다" 라 통제가 어렵고 시간이 오래 걸림
- **소스 근거 + 관측 정합성까지이지 재현이 아니다.** 추측으로 이슈 내면 안 됨

→ PR 본문에서도 "Zed 버그다, 거기 리포트하겠다"는 문장을 **뺐다.**
   지킬 수 없는 약속이고, 확정 못 한 원인을 단정하는 것도 문제다.
   대신 "다른 경로이고 특정 못 했다. 이 패치로는 안 막힌다" 로만 적었다.
